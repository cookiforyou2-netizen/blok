Текущий Package Engine и первый vertical slice принимаем.

Архитектуру ядра больше не перестраивать.

Следующий этап:

CORE-OSH-MVP-01

Цель — превратить существующий модуль «Базовая организация охраны труда» из демонстрации одного документа в минимально законченный коммерческий пакет.

При этом сохранить бесплатный конструктор инструкций без ограничений.

1. Сначала исправить мобильный UX

Работать точечно, без глобального редизайна.

Главная

Сохранить две основные кнопки:

Собрать инструкцию

Сформировать пакет документов

Но уменьшить пустое пространство под ними.

Большой декоративный логотип на мобильном не должен занимать почти отдельный экран.

Он может быть меньше либо располагаться компактнее.

Каталог профессий

Не показывать пользователю внутреннюю формулировку:

«Пять имеют полную модель».

Это техническая информация и создаёт ощущение незавершённого продукта.

Оставить пользовательскую формулировку примерно:

100 профессий

«Выберите профессию. Инструкция будет собрана с учётом выполняемых работ, оборудования, инструмента и условий труда.»

Не раскрывать количество внутренних модулей и степень технической готовности отдельных профессий.

Мастер пакета

На мобильном шесть больших плашек шагов занимают слишком много места.

Оставить сверху:

ШАГ 1 ИЗ 6

и название текущего этапа.

Добавить компактный progress indicator.

Полный список 1–6 можно показывать на широком экране либо в раскрываемом блоке.

Основное содержимое формы должно попадать выше на первый экран.

Администрирование

Сейчас горизонтальный набор вкладок обрезается справа.

Исправить mobile navigation:

- горизонтальный scroll с понятным поведением;
  или
- компактное меню категорий.

Никакая вкладка не должна быть частично недоступна.

В публичной части не показывать технические термины:

- module;
- resolver;
- snapshot;
- applicability;
- full model;

- registerPackageModule.

Система уже знает

Нужно уточнить

Документ требуется

Документ не применяется

Почему включён

Нужны данные

Готов к формированию

Сформирован

3. Довести все 8 документов core_osh до одного механизма генерации

Существующий модуль:

Базовая организация охраны труда

Состав:

1. Приказ о возложении обязанностей по охране труда.
2. Положение о СУОТ.
3. Приказ об утверждении инструкций по охране труда.
4. Перечень инструкций по охране труда.
5. Перечень профессий и должностей.
6. Программа вводного инструктажа.
7. Приказ об организации обучения по охране труда.
8. Приказ о допуске к работе с электроинструментом.

Не создавать для них восемь отдельных UI.

Использовать существующий общий pipeline:

PackageDocument
→ applicability
→ requiredData
→ generatorId
→ templateId
→ preview
→ DOCX.

Первый существующий генератор приказа оставить эталоном.

---

4. Данные организации спрашивать один раз

Создать/доработать единый блок данных для коммерческого пакета.

Например:

- полное название организации;
- сокращённое название;
- адрес;
- ФИО руководителя;
- должность руководителя;
- ответственное лицо за охрану труда;
- должность ответственного;
- дата;
- город.

Если значение уже известно из Organization Profile — использовать его.

Не спрашивать одинаковые сведения заново для разных документов.

Изменение общего реквизита должно использоваться следующими генераторами.

---

5. Перечни должны строиться из профиля

Особенно важно.

Перечень профессий и должностей

Не хардкодить.

Брать фактические профессии, накопленные Organization Profile.

Перечень инструкций

Брать существующие инструкции пользователя и/или определённые системой инструкции.

Не создавать второй каталог.

Если пользователь ранее сформировал инструкцию сварщика — она должна появляться в перечне автоматически.

---

6. Электроинструмент

Приказ о допуске к работе с электроинструментом должен появляться только через Package Engine.

Например обнаружены:

- УШМ;
- дрель;
- перфоратор;
- другой электроинструмент.

Тогда документ определяется правилами applicability.

Если информация UNKNOWN:

Нужно уточнить

Если пользователь явно подтверждает отсутствие:

документ не включается.

Генератор документа сам не решает применимость.

---

7. Предпросмотр

Все документы первого модуля должны использовать единый механизм preview.

В предпросмотре показать:

- название;
- основные реквизиты;
- текст документа;
- основание включения;
- дату формирования.

Не создавать отдельную страницу под каждый документ.

---

8. Формирование пакета

После готовности нескольких документов добавить действие:

Сформировать пакет

Результат:

- каждый готовый документ → DOCX;
- все документы → один ZIP.

Структура архива понятная:

Пакет_ОТ_<Организация>/
    01_Приказы/
    02_Положения/
    03_Программы/
    04_Перечни/
    05_Инструкции/

Если документ имеет статус UNKNOWN или NEEDS DATA, не формировать молча.

Перед созданием пакета показать:

Готово: 6

Нужно уточнить: 1

Нужны данные: 1

---

9. Коммерческий экран пока без оплаты

Платёжную систему пока не подключать.

Но пользовательский путь уже должен выглядеть законченно:

Бесплатный анализ
→ состав пакета
→ заполнение недостающих данных
→ предпросмотр
→ «Полный пакет».

Можно оставить пометку:

Полный пакет

без реальной оплаты.

Не делать искусственных ограничений бесплатного конструктора инструкций.

---

10. Особое внимание содержанию документов

Не генерировать пустые декоративные DOCX.

Каждый документ должен иметь:

- нормальную структуру;
- заголовок;
- реквизиты;
- утверждение/подписание, где требуется;
- содержательную часть;
- связанные данные организации.

Не придумывать нормативные ссылки.

Если нормативное основание ещё не проверено — помечать внутри данных:

"normativeStatus = needs_review"

а не выдавать неподтверждённую норму пользователю как достоверную.

Не добавлять:

- оплату;
- онлайн-кассу;
- подписку;
- СИЗ;

12. Проверка

Проверить мобильный сценарий полностью:

1. Пользователь открывает бесплатный конструктор.
2. Создаёт инструкцию сварщика.
3. Указывает УШМ.
4. Открывает «Сформировать пакет документов».
5. Часть данных уже заполнена автоматически.
6. Система определяет core_osh.
7. Перечень профессий содержит сварщика.
8. Перечень инструкций содержит его инструкцию.
9. Документ по электроинструменту определяется на основании УШМ.
10. Пользователь заполняет общие реквизиты один раз.
11. Документы переходят в состояние «Готов к формированию».
12. Предпросмотр работает.
13. DOCX открываются.
14. ZIP формируется.
15. Бесплатный конструктор продолжает работать как раньше.

После выполнения дать:

- изменённые файлы;
- список 8 генераторов;
- какие сведения общие для пакета;
- какие данные каждый документ требует дополнительно;
- результаты тестов;
- подтверждение mobile QA;
- подтверждение regression бесплатного конструктора.

Главная задача этой итерации:

получить небольшой, но законченный пакет, которым уже можно пользоваться как продуктом, а не очередной архитектурный прототип.
