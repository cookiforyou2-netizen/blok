Фундамент Package Engine принимаем.

Перед следующим этапом сделай только четыре небольших технических исправления:

1. Устрани несогласованность "field: "flag"".

Сейчас основные поля профиля указаны как:

- profession
- work
- equipment
- condition
- hazard

При этом в одном из правил используется:

{ field: "flag", in: ["powerTools"] }

Не оставляй скрытый параллельный механизм признаков.

Либо официально включи "flag" в единую типизированную модель Profile Fact и applicability, либо замени "powerTools" на существующий профильный признак.

Все поля applicability должны проходить через один механизм facts/resolver.

2. Добавь тест пользовательского переопределения:

angle_grinder:
instruction = YES

user = YES
user = NO
user = YES

Итог должен определяться последним явным решением пользователя.

История источников при этом не теряется.

3. Сохраняй Decision Trace для результата документа.

Для каждого документа Package Engine должен иметь возможность вернуть:

{
  result: "YES",

  matchedRules: [...],

  facts: [...],

  sources: [...],

  missing: [...]
}

Чтобы UI мог показать:

«Почему документ включён».

Не делать сложный новый интерфейс — достаточно сохранить данные в модели результата.

4. Добавь "schemaVersion" для сохранённого Organization Profile.

Например:

{
  schemaVersion: 1,
  ...
}

Не создавать пока сложную миграционную систему.

---

После этих четырёх правок перейти к следующему этапу.

ЭТАП: FIRST COMMERCIAL VERTICAL SLICE

Нужно реализовать первый небольшой рабочий коммерческий контур.

Не делать сразу десятки документов.

Цель — доказать весь путь:

Organization Profile
→ Package Engine
→ applicability
→ сбор недостающих данных
→ генерация документа
→ предпросмотр
→ DOCX
→ пакет

1. Создать модуль

Условное имя:

core_osh

Название:

Базовая организация охраны труда

Это не отраслевой preset.

Это базовый модуль документов организации.

2. Количество документов

Для первой версии выбрать примерно 7–10 документов.

Не пытаться сейчас охватить всю охрану труда.

Нам нужен эталонный набор для проверки движка.

Документы должны быть разных типов, чтобы проверить архитектуру:

- приказ;
- положение;
- перечень;
- программа;
- документ с ответственным лицом;
- документ, применимость которого зависит от профиля.

Не копировать документы руками в UI.

Каждый документ должен быть зарегистрирован через существующий Package Module.

3. Карточка документа

Каждый документ должен иметь минимум:

id
name
category
version
status
commercialLevel
applicability
requiredData
templateId
generatorId

Если какая-то сущность уже существует в текущей архитектуре — переиспользовать её.

Не создавать дубли.

4. Required Data

Для генерации документа система должна определять, каких данных не хватает.

Например:

organization.name
organization.director
organization.address
responsiblePerson
approvalDate

Если данные уже известны из Organization Profile — подставлять автоматически.

Не спрашивать повторно.

Если данных нет — документ получает:

READY TO GENERATE

или:

NEEDS DATA

5. Экран пакета

На существующем экране «Пакет документов вашей организации» для документов первого модуля добавить состояния:

Определён
Нужно уточнить
Нужны данные
Готов к формированию
Сформирован

Коммерческий уровень пока можно показывать без реальной оплаты.

Например:

🔒 Полный пакет

Но никакого платёжного шлюза пока не делать.

6. Первый рабочий генератор

Выбрать ОДИН документ из core_osh и провести его полностью до DOCX.

Не делать сразу DOCX для всех документов.

Первый документ должен:

- взять известные данные из профиля;
- запросить недостающие;
- сформировать документ;
- показать предпросмотр;
- позволить получить DOCX.

Архитектура генератора должна быть повторно используемой для следующих документов.

Не делать отдельный уникальный UI только под этот документ.

7. Template / Generator separation

Шаблон и логика определения применимости — разные вещи.

Пример:

PackageDocument
→ applicability
→ requiredData
→ templateId
→ generatorId

Applicability не должен находиться внутри DOCX-генератора.

DOCX-генератор не должен самостоятельно решать, нужен ли документ.

8. Package Snapshot

При начале формирования пакета создать snapshot состава.

Пример:

packageSnapshot = {
  createdAt,
  profileVersion,
  documents: [...]
}

Это нужно, чтобы пользователь видел, какой состав пакета был определён на момент формирования.

Не создавать пока сложное архивное хранение.

9. Не делать на этом этапе

Не делать:

- оплату;
- кассу;
- тарифную систему;
- подписку;
- массовую генерацию всех документов;
- весь модуль СИЗ;
- весь модуль медосмотров;
- весь модуль рисков;
- все отрасли;
- серверную БД профиля;
- полноценный документооборот.

Наша задача — получить один полностью рабочий коммерческий путь.

10. Проверка

После реализации проверить сценарий:

Пользователь бесплатно создаёт инструкцию.

Из инструкции профиль получает профессию и оборудование.

Пользователь открывает:

Сформировать пакет документов

Package Engine анализирует профиль.

Показывает документы core_osh.

Для одного документа система сообщает:

Нужны дополнительные данные.

Пользователь заполняет только недостающие поля.

После этого:

Готов к формированию.

Нажимает:

Сформировать

Получает предпросмотр и DOCX.

После формирования статус:

Сформирован.

При этом бесплатный генератор инструкций продолжает работать без ограничений.

11. Отчёт

После выполнения покажи:

- изменённые файлы;
- новые файлы;
- состав core_osh;
- модель PackageDocument;
- requiredData;
- Decision Trace;
- Package Snapshot;
- какой документ доведён до DOCX;
- как подключается следующий генератор;
- результаты тестов;
- подтверждение отсутствия регрессии бесплатного конструктора.

Не расширяй работу за пределы этого задания.

Главная цель:

не количество документов, а доказанный полностью работающий путь от бесплатной инструкции до персонально сформированного коммерческого документа.
