Текущую реализацию мастера «Сформировать пакет документов» принимаем как основу.

Следующий этап — НЕ добавлять новые коммерческие документы и НЕ расширять UI.

Нужно укрепить архитектурное ядро Package Engine перед дальнейшим наполнением.

Существующий генератор инструкций и текущий пользовательский сценарий не ломать.

1. Исправить модель applicability

Текущая логика слишком общая:

- значения списка = OR;
- поля одного условия = AND;
- несколько условий = OR.

Для будущих нормативных правил этого недостаточно.

Нужна явная декларативная модель:

applicability: {
  all?: [...],
  any?: [...],
  none?: [...]
}

Принцип:

all

Все перечисленные условия должны выполняться.

any

Достаточно выполнения хотя бы одного условия.

none

Ни одно из перечисленных условий не должно выполняться.

Пример:

{
  all: [
    { field: "profession", in: ["welder"] },
    { field: "activities", in: ["welding"] }
  ],
  any: [
    { field: "equipment", in: ["angle_grinder", "drill"] },
    { field: "hazards", in: ["hot_work"] }
  ],
  none: [
    { field: "profile_flags", in: ["activity_not_performed"] }
  ]
}

Не обязательно использовать именно этот синтаксис, если текущая типизация проекта предполагает более подходящий вариант.

Но обязательно должны существовать явные:

- ALL;
- ANY;
- NONE.

Не кодировать сложные правила в UI.

2. Разделить факт и его значение

Не хранить профиль только как набор boolean/string значений.

Нужно предусмотреть происхождение факта.

Каждый накопленный признак должен иметь примерно:

value
source
sourceId
confidence/status
createdAt
updatedAt

Источники:

instruction
user
preset
system
import

Статусы:

inferred
confirmed
rejected

Пример:

equipment.angle_grinder = true
source = instruction
sourceId = instruction-17
status = inferred

3. Приоритет фактов

Ввести понятный resolver.

Приоритет:

1. явное решение пользователя;
2. подтверждённый профиль;
3. автоматически накопленные факты из инструкций;
4. отраслевой preset.

То есть отраслевой preset никогда не должен перезаписывать решение пользователя.

Автоматически найденный факт не должен возвращать признак, который пользователь явно отключил.

Пример:

preset:
work_at_height = true

user:
work_at_height = false

Результат:
false.

4. Не путать FALSE и UNKNOWN

Критически важно.

В системе должны различаться:

YES
NO
UNKNOWN

UNKNOWN означает:

«Мы пока не знаем».

NO означает:

«Пользователь подтвердил, что этого нет».

Не считать отсутствие записи значением false.

Это особенно важно для определения обязательности документов.

Если факт UNKNOWN, документ можно показать со статусом:

«Требуется уточнение».

Если факт NO и нет других оснований применимости — документ исключается.

5. Объяснимость решения

Applicability Engine должен возвращать не только:

applicable = true / false / unknown

но и объяснение.

Например:

applicable: true

reasons:
- profession = welder
- activity = welding
- equipment = angle_grinder

sources:
- instruction-17
- user-profile

Для UNKNOWN:

applicable: unknown

missing:
- work_at_height

Это понадобится UI мастера.

Пользователь должен в перспективе иметь возможность увидеть:

Почему этот документ включён?

Например:

«Документ включён, потому что в инструкции сварщика указаны сварочные работы и использование УШМ».

6. Подготовить Storage Adapter

Сейчас профиль может продолжать физически храниться в browser storage.

НЕ нужно пока создавать полноценную БД и серверную синхронизацию.

Но бизнес-логика не должна напрямую зависеть от localStorage.

Сделать абстракцию уровня:

ProfileRepository / ProfileStorage

примерно:

loadProfile()
saveProfile()
mergeFacts()
setFact()
removeFact()

Текущая реализация:

BrowserProfileStorage

В дальнейшем мы должны иметь возможность заменить её на:

ServerProfileStorage

без переписывания мастера и applicability engine.

7. Отраслевые presets

Preset не является фактом организации.

Preset — только предложение.

Например:

School preset предлагает:

teacher
cleaner
janitor
driver
food_service
ladder

Но эти значения должны иметь:

source = preset
status = inferred

и легко удаляться пользователем.

Preset не должен самостоятельно делать коммерческий документ обязательным без возможности уточнения.

8. Дедупликация

Сохранить существующее поведение:

повторное создание одинаковой инструкции не создаёт дубли фактов.

Но при этом не терять источники.

Если УШМ обнаружена:

- в инструкции сварщика;
- в инструкции слесаря;

факт один:

angle_grinder = true

но sources могут содержать обе ссылки.

9. Версионирование Package Module

Каждый зарегистрированный модуль/документ должен иметь минимум:

id
version
status

status:

draft
active
deprecated

Это понадобится при будущем обновлении нормативной базы.

Не делать пока сложную миграционную систему.

Просто заложить версионность.

10. Тесты

Добавить тестовые сценарии минимум для:

Scenario A

School preset предлагает driver.

Пользователь указывает:

driver = NO.

Документы водителя не должны попасть в пакет.

Scenario B

Инструкция сварщика использовала УШМ.

Profile:

angle_grinder = YES
source = instruction

Applicability документа по ручному электроинструменту получает этот факт.

Scenario C

Пользователь затем явно устанавливает:

angle_grinder = NO

Явное решение пользователя имеет приоритет над автоматически накопленным фактом.

Scenario D

Неизвестно, выполняются ли работы на высоте.

Результат:

UNKNOWN

Документ не считается точно обязательным или точно неприменимым.

UI получает статус:

«Нужно уточнить».

Scenario E

Документ требует:

welder AND welding AND (angle_grinder OR drill).

Проверить корректность ALL + ANY.

Scenario F

Одинаковый инструмент найден в нескольких инструкциях.

Признак не дублируется, источники сохраняются.

11. Что НЕ делать

На этой итерации не делать:

- оплату;
- цены;
- корзину;
- подписки;
- новые коммерческие генераторы;
- десятки новых документов;
- серверную БД профиля;
- переделку существующего генератора инструкций;
- редизайн всей программы.

12. Результат итерации

После работы покажи:

1. какие существующие файлы изменены;
2. какие добавлены;
3. итоговую модель Profile Fact;
4. итоговую модель applicability;
5. resolver приоритетов;
6. Storage Adapter;
7. пример одного зарегистрированного документа;
8. результаты всех тестовых сценариев;
9. подтверждение, что существующий генератор инструкций работает как раньше.

Главный принцип:

Сначала делаем Package Engine достоверным, объяснимым и расширяемым. Только после этого начинаем массово наполнять его коммерческими документами.
