Текущую реализацию функции «Сформировать пакет документов» принимаем как основу.

Следующий этап — укрепить архитектурное ядро Package Engine.

ВАЖНО:

- не переделывать существующий генератор инструкций;
- не ограничивать бесплатную часть;
- не добавлять пока оплату;
- не добавлять десятки новых документов;
- не делать редизайн;
- не создавать второй каталог профессий, оборудования, работ и инструмента.

Нужно доработать именно механизм определения состава пакета.

1. Applicability Engine: ALL / ANY / NONE

Текущей универсальной логики OR/AND недостаточно для реальных нормативных правил.

Нужно реализовать декларативные группы:

applicability: {
  all?: [],
  any?: [],
  none?: []
}

Логика:

ALL — должны выполняться все условия группы.

ANY — должно выполняться хотя бы одно условие группы.

NONE — ни одно условие группы не должно выполняться.

Пример:

applicability: {
  all: [
    { field: "professions", in: ["welder"] },
    { field: "activities", in: ["welding"] }
  ],

  any: [
    { field: "equipment", in: ["angle_grinder", "drill"] },
    { field: "hazards", in: ["hot_work"] }
  ],

  none: [
    { field: "activities", in: ["activity_explicitly_excluded"] }
  ]
}

Конкретную типизацию адаптируй к существующему проекту.

Главное — чтобы Package Engine явно поддерживал ALL, ANY и NONE.

Не хардкодить правила отдельных документов в UI.

---

2. YES / NO / UNKNOWN

Критически важно различать три состояния признака:

YES
NO
UNKNOWN

UNKNOWN:

«Система пока не знает».

NO:

«Пользователь явно подтвердил, что этого нет».

Отсутствие данных НЕ равно NO.

Пример:

Если неизвестно, выполняются ли работы на высоте:

work_at_height = UNKNOWN

Документы по высоте должны получить статус:

Нужно уточнить

а не автоматически включаться или исключаться.

---

3. Источник каждого факта

Профиль организации не должен быть просто набором boolean.

Каждый факт должен хранить происхождение.

Примерная модель:

{
  key: "equipment.angle_grinder",
  value: "YES",

  source: "instruction",
  sourceIds: ["instruction-17"],

  status: "inferred",

  createdAt: "...",
  updatedAt: "..."
}

Допустимые источники:

instruction
user
preset
system
import

Статусы:

inferred
confirmed
rejected

Если один факт обнаружен в нескольких инструкциях, сам факт не дублировать, но сохранить несколько источников.

Например:

angle_grinder = YES

sources:
instruction-welder
instruction-locksmith

---

4. Приоритет фактов

Нужен единый resolver.

Приоритет:

1. явное решение пользователя;
2. подтверждённый пользователем факт;
3. автоматически накопленный факт из инструкций;
4. отраслевой preset.

Пример:

Preset «Автосервис»:

compressor = YES

Пользователь:

compressor = NO

Итог:

NO

Preset никогда не должен возвращать признак, который пользователь явно выключил.

То же относится к автоматически накопленным данным.

---

5. Preset — не доказанный факт

Отраслевые пресеты:

- школа;
- строительство;
- автосервис;
- клиника;
- производство;
- офис;
- склад;
- пищеблок

должны использоваться только как предварительные предложения.

Например School preset может предложить:

teacher
cleaner
janitor
driver
food_service
ladder

Но эти признаки должны иметь низший приоритет:

source = preset
status = inferred

Пользователь может легко подтвердить или удалить каждый из них.

---

6. Explainability — почему документ попал в пакет

Applicability Engine должен возвращать не только:

applicable = true / false

а минимум:

YES
NO
UNKNOWN

и объяснение решения.

Пример:

{
  result: "YES",

  reasons: [
    "profession = welder",
    "activity = welding",
    "equipment = angle_grinder"
  ],

  sources: [
    "instruction-welder"
  ]
}

Для неизвестного:

{
  result: "UNKNOWN",

  missing: [
    "work_at_height"
  ]
}

Это позволит позже показать пользователю кнопку:

Почему этот документ включён?

Пример ответа:

«Документ включён, потому что при формировании инструкции сварщика были указаны сварочные работы и использование УШМ».

---

7. Storage Adapter

Сейчас профиль может продолжать храниться в браузере.

Серверную БД пока НЕ делать.

Но Package Engine и UI не должны напрямую зависеть от localStorage.

Создать слой хранения примерно:

interface ProfileStorage {
  loadProfile()
  saveProfile()
  setFact()
  mergeFacts()
  getFact()
}

Текущая реализация:

BrowserProfileStorage

В будущем должна быть возможность добавить:

ServerProfileStorage

без переписывания Package Engine и мастера.

Не нужно сейчас реализовывать серверное хранилище.

Нужно только правильно отделить storage от бизнес-логики.

---

8. Версионирование package modules

Для каждого документа/модуля предусмотреть минимум:

id
version
status

Статусы:

draft
active
deprecated

Например:

{
  id: "ot-management-order",
  version: 1,
  status: "active"
}

Пока не делать сложную миграционную систему.

Это фундамент для будущих обновлений нормативной базы.

---

9. registerPackageModule сохранить

Существующий принцип:

registerPackageModule(...)

оставить.

Новый отраслевой или функциональный модуль должен добавляться без изменения ядра.

Например в будущем:

auto_service
warehouse
school
welding
work_at_height
vehicle_operation

Модуль может зарегистрировать:

- документы;
- applicability rules;
- дополнительные profile facts;
- зависимости.

Но НЕ должен создавать второй каталог профессий или оборудования.

Использовать существующие ID текущего конструктора инструкций.

10. Обязательные тестовые сценарии

Добавить и реально проверить минимум следующие сценарии.

TEST 1

Preset:

school
driver = YES

Пользователь явно выбирает:

driver = NO

Результат:

документы водителя не включаются только из-за preset.

---

TEST 2

Пользователь создаёт инструкцию сварщика и указывает УШМ.

Профиль автоматически получает:

angle_grinder = YES
source = instruction
status = inferred

---

TEST 3

После этого пользователь в профиле устанавливает:

angle_grinder = NO

Именно NO пользователя становится итоговым состоянием.

Автоматически накопленный YES его не перезаписывает.

---

TEST 4

Система ничего не знает о работах на высоте.

work_at_height = UNKNOWN

Документ получает:

Нужно уточнить

а не YES и не NO.

---

TEST 5

Правило:

welder
AND
welding
AND
(angle_grinder OR drill)

Проверить правильную работу ALL + ANY.

---

TEST 6

Правило:

welding
AND NOT
welding_explicitly_excluded

Проверить NONE.

---

TEST 7

УШМ обнаружена одновременно:

- в инструкции сварщика;
- в инструкции слесаря.

В профиле остаётся один факт:

angle_grinder = YES

но сохраняются оба источника.

---

TEST 8

Повторное открытие или повторная генерация той же инструкции не создаёт дубли.

---

11. Ничего лишнего на этой итерации

НЕ добавлять сейчас:

- оплату;
- цены;
- тарифы;
- корзину;
- подписку;
- генерацию DOCX коммерческого пакета;
- риски;
- СИЗ;
- медосмотры;
- обучение;
- десятки документов;
- серверную БД;
- авторизацию ради пакета;
- новый каталог профессий;
- глобальный редизайн.

Сначала доводим фундамент.
