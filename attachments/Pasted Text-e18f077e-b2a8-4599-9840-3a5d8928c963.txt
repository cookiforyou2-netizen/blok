Сделай отдельный контент-модуль для существующего генератора документов ИОТ.
Модуль: core_osh_suot_v2
Цель: заменить слабое Положение о СУОТ полноценным профессиональным документом, пригодным для генерации под конкретную организацию.
Не меняй приложение, Package Engine, маршруты, UI и существующие генераторы. Нужен только законченный содержательный модуль и спецификация его внедрения терминалом.
Положение должно быть не аннотацией, а полноценным локальным нормативным документом организации.
Структура минимум:
Общие положения
Цели и политика в области охраны труда
Распределение обязанностей работодателя, руководителей и работников
Организация управления охраной труда
Идентификация опасностей и управление профрисками
Обучение и проверка знаний
Инструктажи
Обеспечение СИЗ
Медицинские осмотры
СОУТ
Информирование и консультирование работников
Расследование несчастных случаев и микротравм
Управление подрядчиками
Контроль состояния охраны труда
Планирование мероприятий
Мониторинг и оценка эффективности СУОТ
Документирование и хранение документов
Постоянное улучшение СУОТ
Ответственность
Заключительные положения
Документ должен быть параметризуемым.
Используй placeholders:
{{organization.name}}
{{organization.shortName}}
{{organization.director}}
{{organization.directorPosition}}
{{organization.address}}
{{responsiblePerson}}
{{responsiblePosition}}
{{approvalDate}}
{{city}}
Не встраивай технические пояснения, версии модулей, комментарии разработчику и фразы типа «нормативное основание требует проверки».
Не придумывай нормативные ссылки, в которых нет уверенности.
Для всех нормативных положений отдельно сформируй:
normative_basis[]
с полями:
акт;
статья/пункт;
что именно подтверждает;
статус проверки verified / needs_review.
В клиентский DOCX попадут только verified.
Отдельно от текста документа выдай:
MODULE CONTRACT
id
version
requiredData
optionalData
sections
normative_basis
template placeholders
TERMINAL INTEGRATION
Точно опиши:
какой существующий templateId заменить/обновить;
какой generatorId использовать;
какие данные брать из Organization Profile;
какие данные нельзя спрашивать повторно;
какие тесты терминал должен добавить;
что считается успешной генерацией.
QUALITY GATE
Перед выдачей проверь:
документ не короче полноценного положения;
нет пустых разделов;
нет продуктового языка;
нет технических терминов приложения;
нет повторяющихся абзацев;
нет противоречий между разделами;
обязанности распределены по ролям;
есть процедуры, а не только декларации;
документ можно отдать работодателю после подстановки реквизитов.
Результат нужен как готовый модуль для передачи терминальному агенту. Не внедряй его в приложение сам.
