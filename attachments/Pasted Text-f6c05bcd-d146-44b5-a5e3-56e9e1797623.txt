Нужно доработать текущую программу-конструктор инструкций по охране труда и заложить в неё новый модульный коммерческий контур.

ВАЖНО:
не переписывай существующую программу с нуля;
не ломай текущий генератор инструкций;
не ограничивай бесплатную часть;
не делай пока оплату;
не делай пока полный набор коммерческих генераторов;
сначала правильно заложи архитектуру.

1. Текущая логика продукта

Сейчас система бесплатно формирует инструкции по охране труда.

В базе уже около 100 профессий.

При формировании инструкции учитываются:

- профессия;
- тип выполняемых работ;
- используемое оборудование;
- ручной электроинструмент;
- дополнительные опасности;
- типовые риски;
- особенности рабочего процесса.

Для части профессий уже реализована более сложная логика:
профессия → вид работ → оборудование → инструмент → дополнительные условия.

Эту систему необходимо сохранить и использовать как источник данных для дальнейшего формирования полного пакета документов организации.

2. Основная новая функция

Добавить в систему крупную функцию:

«Сформировать пакет документов»

Это начало будущего коммерческого контура.

Но сейчас задача — не продажа и не оплата.

На первом этапе система должна уметь:

1. собрать профиль организации;
2. использовать данные, которые пользователь уже вводил при создании инструкций;
3. определить, какие документы по охране труда потенциально нужны этой организации;
4. показать пользователю состав будущего пакета;
5. определить, каких данных не хватает;
6. подготовить архитектуру для последующего подключения генераторов документов.

3. Главный архитектурный принцип

Не делай отраслевые пакеты отдельными жёстко прописанными наборами.

Не должно быть логики вида:

school_package = [...]
construction_package = [...]
office_package = [...]

Вместо этого должна быть модульная система правил.

Пакет документов должен собираться динамически из признаков организации.

Пример:

Организация:

- школа;
- 45 сотрудников;
- учителя;
- уборщики;
- дворник;
- водитель;
- электрик;
- пищеблок;
- автомобиль;
- лестницы;
- электроинструмент.

Система должна сама определить применимые модули и состав документов.

Другая школа без транспорта, электрика и пищеблока должна получить другой состав пакета.

4. Создать единый профиль организации

Нужно создать сущность/структуру Organization Profile.

Она должна в перспективе хранить минимум:

- название организации;
- ИНН;
- вид деятельности;
- отрасль;
- количество работников;
- подразделения;
- профессии;
- должности;
- оборудование;
- инструмент;
- транспорт;
- опасные виды работ;
- работы повышенной опасности;
- наличие высотных работ;
- наличие электроустановок;
- наличие пищеблока;
- наличие склада;
- наличие производственных помещений;
- используемые материалы;
- опасности;
- типовые риски;
- признаки СОУТ;
- обучение;
- СИЗ;
- медосмотры.

На первом этапе часть полей можно оставить необязательной.

Главное — сделать структуру расширяемой.

5. Использовать уже введённые пользователем данные

Очень важно.

Если пользователь ранее создавал инструкцию, например:

Профессия: сварщик
Тип сварки: РДС
Оборудование: сварочный аппарат
Инструмент: УШМ, дрель
Дополнительно: баллоны, работы на высоте

эти признаки должны сохраняться в профиле организации.

При нажатии «Сформировать пакет документов» система НЕ должна спрашивать всё повторно.

Используй уже накопленные данные.

Если данных не хватает — спрашивай только недостающие.

7. Механизм applicability

Нужен универсальный механизм определения применимости документа.

Условный пример:

Документ:
«Приказ об организации работ на высоте»

applicability:

- activity = work_at_height

Документ:
«Инструкция по охране труда для водителя»

applicability:

- profession = driver

Документ:
«Документы по медицинским осмотрам»

applicability:

- profession или hazard требует обязательного медосмотра

Документ:
«Положение о СУОТ»

applicability:

- требуется для организации в целом.

В дальнейшем мы будем расширять эти правила.

Поэтому правила должны добавляться через данные/модули, а не через переписывание основного кода.

8. Экран «Сформировать пакет документов»

Добавить заметную кнопку в текущем интерфейсе:

Сформировать пакет документов

После нажатия открыть отдельный мастер.

Желательно сделать 5–7 простых шагов.

Например:

Шаг 1. Организация
Шаг 2. Сотрудники и профессии
Шаг 3. Работы и оборудование
Шаг 4. Опасности и специальные условия
Шаг 5. Проверка данных
Шаг 6. Состав пакета

Если часть данных уже известна — автоматически заполнить.

Показывать прогресс:

Шаг N из 6.

9. Итоговый экран

На последнем шаге пользователь должен увидеть не цену, а результат анализа.

Например:

Пакет документов вашей организации

Определено автоматически:

✓ 7 приказов
✓ 11 инструкций
✓ 3 положения
✓ 4 программы обучения
✓ 5 перечней
✓ 4 журнала
✓ документы по СИЗ
✓ документы по медосмотрам

Всего: 38 документов.

Разделить документы по категориям:

- Организация охраны труда
- Инструкции
- Обучение
- СИЗ
- Медосмотры
- Оценка рисков
- Работы повышенной опасности
- Журналы
- Перечни
- Дополнительные документы

10. Статусы документов

Для каждого документа показывать статус:

✓ данные определены
! необходимо уточнить
○ дополнительный модуль
🔒 генерация будет доступна в полном пакете

Но сейчас НЕ нужно реализовывать оплату.

Коммерческий документ пока можно показывать как будущую функцию.

11. Бесплатная часть

Текущий генератор инструкций остаётся бесплатным.

Никаких ограничений вида:

- 1 инструкция бесплатно;
- только 3 профессии;
- скачивание после оплаты.

Не внедрять.

Бесплатный инструмент должен быть полезным сам по себе.

Его задача — постепенно формировать профиль организации.

12. Отраслевые пакеты

В будущем старые пакеты типа:

- школа;
- строительство;
- автотранспорт;
- офис;
- производство;
- склад

должны стать не отдельными продуктами, а стартовыми отраслевыми пресетами.

Например:

Выбрана «Школа».

Система автоматически предлагает:

- учитель;
- уборщик;
- дворник;
- водитель;
- электрик;
- пищеблок;
- лестницы;
- электроинструмент.

Пользователь может убрать лишнее и добавить своё.

Отраслевой пресет должен только предварительно заполнять профиль.

Он НЕ должен определять пакет жёстко.

13. Архитектура будущей коммерции

Сейчас только предусмотреть уровни:

FREE
PACKAGE
PRO
EXPERT

Но не реализовывать платёжный шлюз.

Пример:

FREE:

- генератор инструкций;
- профиль организации;
- анализ;
- определение состава документов.

PACKAGE:

PRO:

- СИЗ;
- обучение;
- медосмотры;
- дополнительные модули.

EXPERT:

- проверка специалистом ПЦОТ.

Сейчас достаточно предусмотреть поле commercial_level.

14. Необходимо предусмотреть модульное пополнение

Это критично.

Мы должны иметь возможность позже добавить отдельный модуль:

«Склад»

или:

«Сварочные работы»

- опасности;
- правила применимости;
- документы;

module: auto_service

documents:

16. Что должно быть готово после этой итерации

Минимальный результат:

1. существующий генератор инструкций работает как раньше;
2. введённые данные сохраняются в профиль организации;
3. есть профиль организации;
4. есть архитектура document modules;
5. есть универсальная логика applicability;
6. есть кнопка «Сформировать пакет документов»;
7. есть мастер уточнения данных;
8. система формирует предварительный состав пакета;
9. есть экран результата;
10. коммерческие документы пока не генерируются;
11. архитектура позволяет добавлять новые модули без переписывания ядра.

17. UX

Интерфейс должен выглядеть как серьёзная профессиональная система охраны труда.

Не интернет-магазин.

Не делать яркие рекламные карточки.

Белый фон, синий и зелёный акцент.

Крупные понятные элементы.

На экране должно быть понятно:

- что система уже знает;
- что определено автоматически;
- что нужно уточнить;
- что войдёт в будущий пакет.

Название раздела:

Пакет документов вашей организации

Подзаголовок:

Система определит необходимые документы на основании деятельности, профессий, оборудования и условий работы.

18. Перед изменениями

Сначала:

1. изучи текущую структуру проекта;
2. найди существующий генератор инструкций;
3. найди структуру 100 профессий;
4. найди текущую систему модульного пополнения;
5. найди, где сохраняются параметры профессии, оборудования и инструмента;
6. определи, какие существующие сущности можно переиспользовать.

Не создавать параллельные дубли существующих сущностей.

После анализа покажи:

- какие файлы будут изменены;
- какие новые файлы будут добавлены;
- текущую архитектуру;
- предлагаемую архитектуру;
- как будет выполнена миграция без потери существующих данных.

После этого переходи к реализации.

19. Главное правило

Инструкция — это не изолированный документ.

Каждое действие пользователя в бесплатной части должно постепенно формировать цифровой профиль его организации.

Этот профиль в дальнейшем используется системой для автоматического подбора полного пакета документов по охране труда.

То есть цепочка продукта должна быть:

Бесплатная инструкция → накопление данных → профиль организации → анализ → состав пакета → будущая коммерческая генерация.

Архитектуру строить именно под эту цепочку.
